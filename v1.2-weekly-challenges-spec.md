# v1.2 Spec — Weekly Challenges

**Goal:** A Forza-Horizon-playlist-style weekly rhythm: one themed challenge per week, announced Monday by push, entries are normal posts tagged with the challenge hashtag, a winner featured Sunday. Gives lapsed users a reason to open the app every Monday and generates feed content on a schedule — solves the quiet-feed problem at low user counts.

**Why it's cheap:** entries reuse the 1.1 hashtag system (`build_entries.tags` + GIN index), announcements reuse the `send-push` edge function and `device_tokens`, discovery reuses trending chips. The new surface is one table, one screen, one banner, and two scheduled pushes.

---

## 1. UX flows

### The weekly loop
- **Monday 18:00 UK** — push: *"This week's challenge: Engine Bay Week 🔧"*. Challenge banner goes live.
- **All week** — banner at top of Feed + Discover: theme name, emoji, countdown ("3 days left"), entry count. Tap → challenge screen.
- **Challenge screen** — description ("Show us what's under the bonnet"), grid of entries (posts carrying the tag, newest first), a big **"Enter this week's challenge"** button → opens `create_post_screen` with the challenge tag pre-filled and locked-in as a chip.
- **Sunday evening** — you pick a winner (admin). Push to all: *"🏆 Engine Bay Week winner: Hector's Civic"*. Winner pinned on the challenge screen + Discover for 24h, badge added to the car.
- **Monday** — next challenge, cycle repeats. Previous challenges collapse into a browsable archive on the challenge screen ("Past challenges" → winners gallery).

### Entering
Entering *is posting* — no separate flow. A post counts as an entry if it carries the challenge tag and was created inside the challenge window. Users can also just type the hashtag manually on a normal post; it counts the same (the tag is the membership).

### Badges
Winning adds a permanent badge row on the car's detail page: 🏆 *Engine Bay Week — Aug 2026*. Badges accumulate. That's the trophy cabinet — visible on the public share page too (ties into the share-links spec).

### Guest mode
Guests see the banner, the challenge screen, and entries (it's all public reads). Entering requires an account — the CTA routes through the existing auth gate. Challenges become an acquisition hook, not just retention.

## 2. Data model (migration `0037_challenges.sql`)

```sql
-- One row per weekly challenge.
create table if not exists public.challenges (
  id           uuid primary key default gen_random_uuid(),
  title        text not null,                    -- "Engine Bay Week"
  emoji        text not null default '🏁',
  tag          text not null unique,             -- normalised, no '#': "enginebayweek"
  description  text not null default '',
  starts_at    timestamptz not null,
  ends_at      timestamptz not null,
  winner_entry_id uuid references public.build_entries(id) on delete set null,
  winner_announced boolean not null default false,
  created_at   timestamptz not null default now(),
  constraint challenge_window check (ends_at > starts_at)
);

create index if not exists idx_challenges_window on public.challenges (starts_at, ends_at);

-- Badges: one per (car, challenge) win.
create table if not exists public.car_badges (
  car_id       uuid not null references public.cars(id) on delete cascade,
  challenge_id uuid not null references public.challenges(id) on delete cascade,
  awarded_at   timestamptz not null default now(),
  primary key (car_id, challenge_id)
);

-- Reads are public (guest mode parity); writes are service-role only
-- (admin picks winners, scheduler creates challenges).
alter table public.challenges enable row level security;
alter table public.car_badges enable row level security;

create policy "challenges public read" on public.challenges for select using (true);
create policy "badges public read"     on public.car_badges  for select using (true);

grant select on public.challenges, public.car_badges to anon, authenticated;

-- Entries query (no new table needed — the tag IS the membership):
--   select * from build_entries
--    where tags @> array[:tag]
--      and created_at between :starts_at and :ends_at
--    order by created_at desc;
-- Uses idx_build_entries_tags (GIN) from 0035.
```

Notification pref (same migration), following the `0015` pattern:

```sql
alter table public.notification_prefs
  add column if not exists challenge_updates boolean not null default true;
```

**No entries table.** Tag + time-window containment is the membership test. One less write path, no sync bugs, manual-typed hashtags count automatically. The GIN index makes it fast at any realistic scale.

## 3. Scheduling & push (edge function `challenge-tick`)

One new edge function, invoked by **Supabase Cron** (or pg_cron → `net.http_post`) on two schedules:

- **Mon 18:00 Europe/London** — finds the challenge whose window just opened; sends *"This week's challenge: {title} {emoji}"* to all `device_tokens` where `notification_prefs.challenge_updates` (reusing `send-push` internals/payload shape). No challenge scheduled → does nothing, silently.
- **Sun 19:00 Europe/London** — finds the just-ended challenge; if `winner_entry_id` set and not yet announced, sends *"🏆 {title} winner: {car nickname}"*, inserts the `car_badges` row, marks `winner_announced`.

DST note: schedule the cron in UTC but compute "is it 18:00 London" inside the function, or just accept the hour shift twice a year — at current scale, accept it and revisit.

**Failure mode:** if you forget to pick a winner by Sunday, nothing sends — no broken push, the challenge just archives winnerless. Pick late and the badge/announcement still works on the next tick.

## 4. Admin

Minimum viable (no new admin UI): insert rows via the TorqueDenAdmin app's SQL/data pane or Supabase Studio — schedule 4–8 weeks of themes in one sitting.

Proper (phase 2, `TorqueDenAdmin/Screens/`): a Challenges screen — list scheduled/past, create/edit, and a winner-picker that lists entries for the ended week and sets `winner_entry_id` in one click.

Winner picking in-app (alternative): extend `lib/screens/admin_screen.dart` with the same — whichever surface you actually use day-to-day. Recommend TorqueDenAdmin since Sunday-evening judging fits desktop.

## 7. Phases

**Phase 1 (one evening of themes + core loop):** migration, banner, challenge screen, pre-filled tag posting, manual challenge inserts, manual winner pick in Studio, Monday push via manual `send-push` invoke if cron isn't wired yet.
**Phase 2:** `challenge-tick` cron automation, badges on car pages, past-challenge archive, admin winner-picker UI.
**Phase 3:** entry reaction-count leaderboard on the challenge screen (community signal for your winner pick), "streak" for entering N weeks running, seasonal meta-themes.

## 8. Edge cases

- Two challenges overlapping → prevented operationally (schedule non-overlapping); banner shows the one whose window contains `now()`, ties broken by latest `starts_at`
- Deleted winning post → `winner_entry_id` nulls (FK `set null`); badge persists (it was earned); challenge screen shows "winner" card gracefully without the post
- Tag squatting (posting the tag outside the window) → window check excludes it from entries; harmless otherwise
- Tag collisions with organic hashtags → pick distinctive tags (`enginebayweek`, not `engine`); uniqueness constraint on `challenges.tag` prevents reuse across weeks
- Zero entries in a week → banner still counts down honestly; you post an entry yourself (founder-seeded content is normal at this stage); no winner push if none picked
